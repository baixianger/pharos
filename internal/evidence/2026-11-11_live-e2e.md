Key results (real codex-cli 0.167.0, ChatGPT auth; auth material never printed):

- `phase="final_answer"` **exists** on 0.167: the completed turn's `agentMessage` item is `{type:"agentMessage", text:"PONG", phase:"final_answer"}` (both a live `item/completed` notification and `thread/read {includeTurns:true}`). Unit-tested (7 tests); the PASS run above did not need the fallback (`replyPolls:2`), so its live use remains unproven.

## B. DSH reply write-back — selected approach: plugin calls Rust `thread.reply` (approach B)

Chosen because the loop stays where the vendor session lives (`integrations/dsh-plugin-pharos`) and `rust/crates/pharos-adapter-dsh` stays thin (it only declares capabilities; no Thread-loop logic moved into Rust). **This is a Lead decision, user-overridable**: the canonical alternative is the DSH mesh tool (`pharos_mesh_send`); disabling write-back is dropping the plugin's `thread.reply` call (no Rust change).

Rust runtime (commit `c43e985`, file `rust/crates/agent-runtime/src/thread_reply.rs`, minimal `main.rs` wiring):

- New additive JSON-RPC `thread.reply` `{room, asMember, text, messageId?}`; response is `pharos_api::ReplyThreadMessageResponse` = `{ok, thread, as, replyId, replyTo}`; `ok` only after the row persisted.
- Reply goes through `pharos-thread` `replyOnce`: stable id from `(scope, room id, member, original message id)` → an identical retry returns the **same** `replyId` and never inserts a second row; conflicting text for the same anchor is an error, never overwritten. Unknown room / unknown-or-unaddressed `messageId` / empty fields / >1 MiB text are explicit `-32602` errors; unknown members auto-join with the deterministic nick.
- Thread replica is opened lazily and re-resolved under the runtime `--thread-data-dir` (the web data dir, whose replica is `<data-dir>/mesh/replica.sqlite3`). `runtime.hello` advertises `thread-reply-v1`.
- 10 new unit tests (idempotent replay same reply id + one row, conflict rejection, missing anchor, auto-join, unknown room, empty/oversized input, capability, store parity).

Plugin (commit `dc42874` + real-host fixes in `3b271bf`):

- After `agent.followup` the plugin correlates the injected user-message id to the DSH turn (`agent/inbox/claimed`) and on that turn's `session/event turn/end` posts **once** via `thread.reply` with the turn's final assistant text (text blocks of the last non-empty `assistant/message`; multi-step narration is never concatenated). Bounded 3× retry on RPC failure, stderr logging; no assistant text / no room+messageID anchor → **nothing is written** (logged); delivery ack semantics unchanged (`poll → injected → followup → consumed` still does not claim assistant completion).
- Two real-host incompatibilities were found only by the live DSH run and fixed: (1) DSH session-format v4 rejects the retired generic user-message `source.kind = "plugin"` — the message now uses the producer-owned `plugin:dsh-plugin-pharos-runtime`; (2) an idle DSH agent wakes **synchronously inside `agent.followup`**, so `agent/inbox/claimed` can fire before followup returns — correlation is now reserved before the handoff and rolled back when the handoff throws.
- 30/30 `node --test` cases (18 pre-existing contract tests + 12 write-back tests incl. synchronous-claim ordering, failed-handoff rollback, final-answer-only selection, replay dedupe, bounded retries).
- `PHAROS_PLUGIN_DEBUG=1` adds stderr diagnostics for live E2E (reservation/claim/turn-end); never prints prompt bodies.
