# DSH 在 Thread 中的状态与通信

**Host-owned product 投递桥（2026-11-09）**：新增 `DshThreadRuntimeBridge`，与 Agy 路径同构：Host binder 注册 Runtime conversation → `delivery.poll` → `DshLiveSessionService.send(turnID:)` → product `replyOnce`（非 Broker `say-once`）。桌面仅在 `isProductModeEnabled` 下对本机显式绑定的 DSH 启动该桥；legacy 仍由项目插件消费 Broker。受控 fixture `testDshHostProductPathUsesReplyOnceWithoutBroker` 通过。`PHAROS_HOST_THREAD_DSH_PRODUCT_PATH_TEST=1` 隔离 `DSH_HOME` Session 创建成功，但种子回合 90s 未完成 → live **not-tested**。证据：`internal/evidence/2026-11-09_phase-b2-dsh-codex-product-bridges.log`、`...phase-b2-dsh-live-product-path.log`。

**远程架构状态（2026-11-08）**：Broker → 远端 Pharos 节点 → 本机 Runtime 的投递方向符合目标，但候选清单直接读取远端 DSH，节点身份也直接经 SSH 读取文件；这仍是混合路径，真实远端 Agent 往返尚未验收。迁移范围见 [架构决策与审计](../../../RFC-006-UNIFIED-CLIENT-AND-BACKEND-INTEGRATION.md#remote-pharos-boundary-and-current-deviations)。

远程节点领取 Runtime 投递后回执迟到时，旧 Broker 可能同时将消息放入旧 mailbox；现已区分未知结果，具体修复与剩余恢复要求见 [交接第 100–101 项](../../../handoff.md)。未证明真实 DSH 重复执行，远程 Thread 不应视为已验证可靠投递。

过期但已领取的投递现可在严格匹配命令和 RPC ID 后记录迟到成功；受控证据及历史对账缺口见 [交接第 102 项](../../../handoff.md)。

后续已接入持久确认与历史投影，Runtime 接收不代表 DSH 执行；具体证据与恢复限制见 [交接第 103 项](../../../handoff.md)。

明确远程 host 的成员不再先投递到本机同 ID Runtime；测试与远程环境边界见 [交接第 104 项](../../../handoff.md)。

有显式节点 owner 时还须核对节点来源，含无 host 和离线 owner 的受控测试；范围见 [交接第 105 项](../../../handoff.md)。

### 远程绑定只读检查基础（2026-11-08）

Rust Runtime 新增 `delivery.inspect-dsh-binding`：输入一个 `sessionID`，只返回 `eligible`。它复用实际投递候选规则，要求唯一、新鲜在线、驱动轮询，DSH 的 vendor Session ID 和成员 ID 精确一致，且驱动声明 `mesh.reply-once-v1`；无匹配、冲突、过期或旧插件都返回 false。空或超过 512 字节的 ID 被拒绝，检查不注册会话或产生投递；`runtime.hello` 声明 `dsh-binding-inspect-v1`。受控 Host RPC 网关允许这个单 Session 检查，原有可批量读取详情的 `delivery.inspect-members` 仍仅供本地驱动调用。

Rust 测试覆盖路由条件、冲突、旧插件、过期及无投递，17 项通过（`internal/evidence/2026-11-08_remote-dsh-inspection-rust-final.log`）；真实 Rust socket + 项目插件注册的检查和其他插件回归 4 项通过（`...remote-dsh-inspection-plugin.log`）；Swift AgentRuntimeClient 经真实 Rust socket 调用新方法、拒绝旧批量详情方法。均在本机隔离环境运行。

### 远程桌面绑定（2026-11-08）

新增受限批量方法 `delivery.inspect-dsh-bindings`，每次最多 300 个精确 Session ID，按顺序仅返回 eligibility；不暴露原有成员详情。Runtime 宣告 `dsh-binding-batch-inspect-v1`，旧节点不提供候选。桌面通过已有 SSH 连接只读目标机器的节点 ID 和主机名，与 Broker 中唯一、新鲜在线且来自远端的节点匹配，再经该节点检查 DSH Session；加入前重新读取身份、检查 Session 和连接，Broker 提交时再次核验节点在线与归属。这些是检查时的快照，不能保证之后驱动持续在线或 Agent 已消费消息；节点来源与主机名匹配也不等同于密码学主机身份认证。

隔离测试使用 mac-air 的真实只读 SSH 身份、模拟远端节点和 Session 清单，以及本机真实 Rust Runtime 和模拟驱动：程序操作 WebKit 加入后，定向消息进入 Runtime 队列一次，旧节点与离线节点被拒绝；没有运行真实远端 DSH 消费者或验证回复（`internal/evidence/2026-11-08_remote-dsh-binding-ssh-ui-fixture-final2.log`）。批量 Rust 测试 17 项、真实 Rust socket 加项目插件测试 4 项通过（`...remote-dsh-binding-batch-rust.log`、`...remote-dsh-binding-batch-plugin.log`）；路由和桌面相关 Swift 回归 30 项通过（`...remote-dsh-binding-regression.log`）。mac-air 现有旧测试副本不具备新能力，未向远端安装、同步或重启组件；真实跨机投递、消费、回复及故障恢复仍待验证。

本机真实 DSH UI 绑定回归首次等待 120 秒未见回复，结束时无相应 Runtime 投递记录，发送前 journal 未变（`...remote-dsh-binding-local-live-regression.log`）；后续开启诊断的重试中，同一流程出现一次 Runtime 投递、真实 Session 完成及 Thread 回复（`...remote-dsh-binding-local-diagnostic.log`）。首次失败根因未查明，成功重试不能消除这一不确定性。

### Runtime 回执身份校验（2026-11-08）

受控复现发现，即时 Runtime 回复只检查 `submitted`，错误 JSON-RPC ID 的回复会被误判为已接收；本机 Runtime 客户端还会先解释错误内容，可能把其他请求的“无成员”错误误判为安全回退。现要求本机 socket 回应的 JSON-RPC 版本及 ID 匹配请求后才解释错误；本机和远程即时投递成功也必须匹配原请求 ID、版本及布尔 `submitted`，远程与迟到确认使用相同的身份检查。不匹配保留 unknown，不进入备用 mailbox。复现和 28 项回归证据分别见 `internal/evidence/2026-11-08_runtime-ack-id-repro.log` 和 `...runtime-ack-id-regression-final.log`；实际 Unix socket 上模拟了错误 ID 的错误响应。带真实 SSH 身份的模拟节点/UI 绑定及正向 Runtime 入队再次通过（`...runtime-ack-id-remote-ui.log`），仍未运行真实远端 DSH 消费者。模拟错误回执不代表观察到真实 Agent 出现此故障。原始投递过程中 Broker 崩溃、多目标顺序超时和真实断网仍待处理。

### 原消息先落盘再投递（2026-11-08）

受控测试复现了 Runtime 在投递返回前同步回复时，Broker 因原消息尚未写入历史而拒绝关联回复；原消息写入失败时旧代码仍调用了 Runtime（`internal/evidence/2026-11-08_thread-persist-before-route-repro.log`）。现在 Broker 先原子写入原消息，初始将目标标为 unknown，再开始路由；保存失败即拒绝发送。路由结束时在同一 transcript 锁下仅替换原消息状态，保留期间到达的回复；状态更新失败保留保守的 unknown。消息事件在初始落盘后发出一次，事件携带初始状态；最终状态读取发送响应或刷新历史。投递中重新打开 Broker 的受控测试能读取原消息及 unknown，但并未杀死 Broker 或模拟断电。

真实本机独立 DSH Host、项目插件和 Rust Runtime 经桌面 WebKit 绑定并完成定向消息、Runtime 完成、Session journal 和关联房间回复（`internal/evidence/2026-11-08_thread-persist-before-route-dsh-live.log`，测试 Session `session-57f181dc-61af-4555-b2b0-f8c056c2842a` 保留）。这是正常真实回归，快速回复竞态本身使用模拟 Runtime。最终路由、事件和房间身份回归 83 项通过（`...thread-persist-before-route-regression-final.log`）。原子替换会读取并重写整个房间 transcript，长历史的性能、跨 Broker 进程同时写入、真实进程崩溃与断电恢复均未验收；多目标顺序超时及真实远端 DSH 消费仍未解决。

### 投递中的房间与成员变更（2026-11-08）

受控测试复现投递过程中删除房间导致已发送原消息从历史消失（`internal/evidence/2026-11-08_thread-room-mutation-inflight-repro.log`）；按旧控制流，后续 fallback 还可能访问已移除房间，但此次没有通过崩溃测试验证该推断。Broker 现按房间跟踪正在路由的发送；期间删除、改名、成员离开和同名成员接管会返回“投递进行中，请重试”，全部发送结束或写入失败后解除限制；加入已有同一成员仍可进行。发送取得保护时会重新核验显式发送者身份。删除期间持有房间状态锁直到 transcript 删除完成，避免同一 Broker 内新的发送和删除文件交错。

隔离测试覆盖受控删除/改名/离开/接管、两个并发发送与失败后释放保护；真实 Broker Unix socket 配合模拟远程节点未领取命令，验证投递中拒绝更改、完成 fallback 后保留消息及允许改名，相关 85 项回归通过（`internal/evidence/2026-11-08_thread-room-mutation-inflight-final.log`）。这未验证真实远端 Agent、跨 Broker 多进程并发或用户界面如何呈现拒绝。此保护不限制同房间并发发送，等待时间仍由各目标路由决定，多目标顺序超时未解决。

### 多目标等待与发送响应丢失（2026-11-08）

真实隔离 Broker socket 配合一个模拟远程节点，四个目标各持有命令约 7.8 秒后报告失败：旧客户端在 Broker 完成前以 30 秒固定等待超时，返回“invalid response”，而历史已有原消息（`internal/evidence/2026-11-08_thread-multiple-target-timeout-repro.log`）。常用 `send` / `sendIfUp` 的 `say` 现在按去重目标数量计算等待预算，为每个目标预留本机 Runtime 与远程节点等待，并保留基础余量；目标数按 100,000 截断参与计算。这个估算不能保证在极端慢 I/O、超量目标或网络故障下永不超时，显式 endpoint 的 `send(..., to:timeoutSec:)` 仍使用调用方指定的超时，Broker 仍逐目标顺序路由。

对于建立连接后响应丢失或无法解析的 `say`，客户端现在提示结果未知、重试前检查 Thread 历史；这不意味着消息一定已送达。真实 Unix socket 受控关闭测试验证提示，WebKit 静态状态渲染测试检查提示可见；未模拟真实断网或完成从断网到 UI 的端到端验收。修复后四目标受控 socket 测试、事件/路由及 UI 回归 90 项通过（`internal/evidence/2026-11-08_thread-multiple-target-timeout-verified.log`）。先前一轮相关回归暴露同一消息事件先于发送确认时界面可能重复（`...thread-multiple-target-timeout-final.log`）；现按服务端消息 ID 合并确认与事件，保留不同 ID 的同文消息和先到事件回执。后续调整后单独运行的 Thread/界面回归 10 项通过（`...thread-send-reconciliation-final.log`）。

## 共同的 Thread 通信路径（源码）

桌面 Thread 是 Pharos Mesh room，不是厂商自己的 Session 对象。`DesktopPharosClientService` 在 Broker 模式使用 `list`、`who`、`history` 和 `say`；分布式模式调用 Mesh chat 接口。成员使用不可变 member ID；界面加载 roster 时读取 member 的 `kind`、`host`、`state` 等，缺失状态为 `unknown`。文本里的 `@name` 被解析为定向目标；Broker 源码只为显式目标建立 mailbox，普通聊天不等于向所有 Agent 投递。Runtime 桥尝试用 `delivery.submit-member` 携带 member ID、消息 ID、room、sender 和幂等键；未由 Runtime 接受时，Broker 保留 mailbox 并走保守的唤醒路径。详情见 [桌面服务](../../../../Sources/Pharos/UI/Shell/DesktopPharosClientService.swift)、[Runtime 投递桥](../../../../Sources/PharosRuntime/MeshRuntimeDeliveryBridge.swift) 和 [Broker](../../../../Sources/PharosMeshCore/MeshBroker.swift)。

Thread 视图每 3 秒刷新最近 200 条历史和当前 roster；右栏显示 member 的 Mesh 状态，读取失败的成员显示 `unknown`，model/mode 留空。状态是 Broker `who` 或分布式 Mesh 已有的 presence 快照，不是厂商状态的直接证明；该视图虽处理 `memberStatusChanged`，当前生产服务没有发出该事件，因此这里是轮询而非推送。隔离真实 Broker 测试验证了 unknown → busy 自动刷新、blocked 刷新，以及 room、成员、发送和 mailbox；WKWebView 测试确认状态文本显示。各家真实 hook/driver 上报、分布式 Mesh、桌面到真实代理投递与回复仍需验收。桌面消息历史目前统一显示 `unverified_fallback`：房间落盘、Runtime 入队和 mailbox 领取本身都不证明 Agent 已处理消息；生产服务尚未将逐目标消费回执关联回来。隔离真实 Broker 测试验证了发送前后、mailbox 领取后仍保持未验证；这不等于验证了真实 Agent 收到或回复。


2026-11-07 投递边界：Swift Runtime 和 Rust Runtime 的外部插件投递要求驱动声明 `delivery.poll`、最近 15 秒内登记/心跳且会话最近 45 秒在线并未归档；否则回退 Mesh mailbox。Rust Runtime 另有内置 Codex worker：已登记的 managed Codex 会话可进入队列，不依赖插件心跳；它会等空闲、必要时恢复会话并调用 `turn/start`。Swift Runtime 没有这个内置消费者。隔离 Broker + 真实 Unix socket + Swift Runtime 的测试验证队列中的 room、正文、消息 ID；Rust 测试覆盖无领取能力、离线、过期与正常接收。测试没有启动厂商 Agent，队列接收不代表消费。投递后驱动崩溃时消息可能留在 Runtime 队列，同一目标和正文的已入队重试可返回原记录，即使驱动已离线；不同内容或目标复用该键会拒绝。确认丢失导致的两条路径重复、断线恢复和旧队列迁移仍待验证。

## DSH 特有路径与边界

旧 [DSH adapter](../../../../Sources/PharosRuntime/Adapters/Dsh/DshBackendAdapter.swift) 构造 `delivery.submit-member`，源码注释提到 `dsh-plugin-pharos` 的 poll、followup 和 ack；该方法忽略 Runtime 发送错误且返回 delivered，不能作为成功证据。桌面 Thread 使用 Mesh room；实际 plugin 是否安装、消息被领取、注入正确 Session、Agent 回复 room 以及 ack 尚需端到端验证。DSH Session journal 的 turn/Goal/Todo 和 waterfall 审批已接到 Session 服务，但尚无证据证明这些状态已映射到 Thread roster。历史 plugin 配置注意事项见 [项目问题记录](../../../PITFALLS.md)。

项目内 DSH 插件已声明 `delivery.poll` 并等待 `agent.followup()` 返回后才确认 consumed；这里的 consumed 仍只表示插件调用返回，不证明模型完成回复。独立 `~/personal/deepseek harness/dsh-plugin-pharos` 当前源码使用 `native-followup-v1` 而不声明 `delivery.poll`；旧插件需要升级并确保定期更新驱动和会话在线状态，否则新 Runtime 会回退 mailbox。尚未在用户运行中的插件部署该更改。

隔离集成测试使用真实 Rust Runtime、真实项目插件和 `@deepseek-ai/dsh-llm` 消息构造器，以及模拟 DSH Agent：从 `delivery.submit-member` 到指定 Session 的 `followup`，原测试验证在异步 `followup` 返回前仍 queued，之后变为 consumed；后续宿主回复实现改为调用前先记录 injected，见下。未启动真实 DSH Agent 或验证模型回复；`followup` 已返回而 ack 丢失时可能重复注入，尚无跨进程去重证明。复现命令见 [插件 README](../../../../integrations/dsh-plugin-pharos/README.md)。


## 跨 Session 投递隔离（2026-11-07）

项目内插件此前在一个全局轮询中逐个等待 `agent.followup`；根据控制流程，一个未返回的 followup 会阻止后续 Session 的投递轮询和下一次全局 reconciliation。现改为每个 Session 最多一个独立投递任务：同一 Session 仍串行等待 followup 和确认，不同 Session 不互相等待；全局轮询仍负责驱动和状态刷新。异常会记录，后续轮询可重试；followup 已成功但确认失败时仍可能重复注入，不能宣称恰好一次。

`integrations/dsh-plugin-pharos/runtime-integration.test.mjs` 使用真实 Rust Runtime 和插件、两个模拟 Agent：第一会话的 followup 挂起时，第二会话收到并确认投递；第一会话后续消息仍排队，释放后按顺序处理。测试输出 `internal/evidence/2026-11-07_dsh-plugin-session-isolation-retest.log`。首次运行因未安装锁定的 npm 依赖失败，`npm ci --ignore-scripts` 后通过。该测试未运行真实 DSH Agent，未验证模型完成、回复房间、异常退出或插件部署到用户运行中的 DSH。


## Runtime 成员身份冲突（2026-11-07）

Swift 与 Rust Runtime 的 `delivery.submit-member` 若有多个符合在线条件的会话匹配同一 member ID，原先选择最近更新的会话，不能证明目标正确。现在新投递遇到多个候选会返回错误，不写入任何 Runtime 队列；只剩一个有效候选后正常路由。已有幂等键的重试仍返回原记录，避免把已接受的投递重新导向其他会话。隔离 Swift Broker + 真实 Runtime socket 测试确认冲突时回退 mailbox，Rust 测试覆盖拒绝和冲突解除；对应输出 `internal/evidence/2026-11-07_runtime-ambiguous-swift-final.log`、`internal/evidence/2026-11-07_runtime-ambiguous-rust-retest.log`。

回退 mailbox 仍以同一个 member ID 寻址：如果多个消费者共享该 ID，不能保证领取者身份；本次只消除 Runtime 按更新时间盲选，不证明端到端无误投。现有已入队记录不会自动迁移，真实多主机冲突、修复身份及重连仍需验证。Antigravity 的 Mesh→ACP 桥仍未完成。

### 冷会话恢复接口调查补充（2026-11-07）

本机 DSH `0.2.2-rc.1` 随安装包附带的 `@deepseek-ai/dsh-agent/README.md` 明确记载插件 API `ctx.agents.resume()`：它从持久 Session 重建 Agent，并返回持有销毁能力的 handle。这是一个受支持的底层原语，但仅有 Session ID 并不足以安全地等价于普通 Host 恢复。对照同版本 `@deepseek-ai/dsh-api-session-controller` 的说明和实现，普通恢复还会读取精确的 Session 投影及 preset、应用模型默认配置和 preset 的 scoped setup，拒绝不属于普通 Session 的 subagent、处理 Session writer 冲突并合并并发恢复。简单调用底层 `resume` 可能跳过这些约束，因而暂未接入生产插件。

该版本 Host 内部存在 `resolveAgent`，注释称供其他 Host API domain 使用，但随包说明没有把它列为外部客户端或第三方插件支持的恢复协议；目前不能将其私有实现当作稳定入口。下一步应查找上游明确支持的、能保留上述普通 Session 策略的插件/API 入口；如无此入口，记录不支持并继续其他 Agent 和远程验证。此处是随安装包源码及文档的静态核对，没有新增真实恢复试验，也不改变此前冷 Session 失败结论。

另一个明确支持的入口是独立 SDK 协议的 `session/resume`：本机 `dsh sdk --help` 确认可启动 stdio SDK，安装包内 `dsh-sdk-protocol` `0.2.2-rc.1` 文档说明此请求使用原持久库恢复确切 Session、不发送新输入，并拒绝占用的 Session。上游 [SDK 协议](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/sdk/protocol/README.md) 和 [SDK Server 说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/sdk/server/README.md) 还说明 SDK 是独立 owner，恢复时可能修复中断回合并将初始化时模型路由记录为 Session 选择。故该请求不是无持久副作用的 Web Host 激活接口；无法在已有 Web Host 占有同一 Session 时作为第二个 writer 使用。是否能够让 SDK profile 安全加载项目插件、保留所需 preset/模型并与桌面历史订阅协调，还未测试。SDK 是下一条可验证的正式路径，而不是已完成的 Web Host 修复；上游 master 文档可能与本机版本不同，实施时以本机版本及实测为准。

### 注册与销毁交错（2026-11-07）

真实 Rust Runtime 前增加可控本机 socket 代理，延迟 `conversation.register` 的响应：Session 在请求尚未返回时销毁，旧实现随后错误地将它注册为 online；回归先失败，见 `internal/evidence/2026-11-07_dsh-register-race-before.log`。插件现在在注册返回和状态更新时核对同 ID 的当前 Agent 身份；旧 Agent 已销毁且没有替代者时，登记离线；若替代 Agent 已出现，等待旧请求结束后注册替代者，迟到的旧销毁事件不会使新 Agent 离线。序号在同一插件进程内保持递增。
