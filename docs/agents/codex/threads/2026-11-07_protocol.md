# Codex 在 Thread 中的状态与通信

**远程架构状态（2026-11-08）**：目标是经远端 Pharos 节点对接本机 Codex；当前桌面尚无远程 Codex Session 的 Thread 绑定入口，不能把本机往返视为远程完成。详见 [架构决策与审计](../../../RFC-006-UNIFIED-CLIENT-AND-BACKEND-INTEGRATION.md#remote-pharos-boundary-and-current-deviations)。

共用 Runtime 投递即时回执现校验 JSON-RPC 请求身份；受控复现、回归与剩余限制见 [DSH Thread 的共同链路记录](../../dsh/threads/2026-11-07_protocol.md)。这不等于远程 Codex 已端到端验收。

共同 Broker 的远程 Runtime 投递此前存在领取后超时回退 mailbox 的重复投递风险；受控复现、修复与未完成事项见 [交接第 100–101 项](../../../handoff.md)。未证明真实 Codex 重复执行。

过期但已领取的投递现可在严格匹配命令和 RPC ID 后记录迟到成功；受控证据及历史对账缺口见 [交接第 102 项](../../../handoff.md)。

后续已接入持久确认与历史投影，Runtime 接收不代表 Codex 执行；具体证据与恢复限制见 [交接第 103 项](../../../handoff.md)。

明确远程 host 的成员不再先投递到本机同 ID Runtime；测试与远程环境边界见 [交接第 104 项](../../../handoff.md)。

有显式节点 owner 时还须核对节点来源，含无 host 和离线 owner 的受控测试；范围见 [交接第 105 项](../../../handoff.md)。

## 共同的 Thread 通信路径（源码）

桌面 Thread 是 Pharos Mesh room，不是厂商自己的 Session 对象。`DesktopPharosClientService` 在 Broker 模式使用 `list`、`who`、`history` 和 `say`；分布式模式调用 Mesh chat 接口。成员使用不可变 member ID；界面加载 roster 时读取 member 的 `kind`、`host`、`state` 等，缺失状态为 `unknown`。文本里的 `@name` 被解析为定向目标；Broker 源码只为显式目标建立 mailbox，普通聊天不等于向所有 Agent 投递。Runtime 桥尝试用 `delivery.submit-member` 携带 member ID、消息 ID、room、sender 和幂等键；未由 Runtime 接受时，Broker 保留 mailbox 并走保守的唤醒路径。详情见 [桌面服务](../../../../Sources/Pharos/UI/Shell/DesktopPharosClientService.swift)、[Runtime 投递桥](../../../../Sources/PharosRuntime/MeshRuntimeDeliveryBridge.swift) 和 [Broker](../../../../Sources/PharosMeshCore/MeshBroker.swift)。

Thread 视图每 3 秒刷新最近 200 条历史和当前 roster；右栏显示 member 的 Mesh 状态，读取失败的成员显示 `unknown`，model/mode 留空。状态是 Broker `who` 或分布式 Mesh 已有的 presence 快照，不是厂商状态的直接证明；该视图虽处理 `memberStatusChanged`，当前生产服务没有发出该事件，因此这里是轮询而非推送。隔离真实 Broker 测试验证了 unknown → busy 自动刷新、blocked 刷新，以及 room、成员、发送和 mailbox；WKWebView 测试确认状态文本显示。各家真实 hook/driver 上报、分布式 Mesh、桌面到真实代理投递与回复仍需验收。桌面消息历史目前统一显示 `unverified_fallback`：房间落盘、Runtime 入队和 mailbox 领取本身都不证明 Agent 已处理消息；生产服务尚未将逐目标消费回执关联回来。隔离真实 Broker 测试验证了发送前后、mailbox 领取后仍保持未验证；这不等于验证了真实 Agent 收到或回复。


2026-11-07 投递边界：Swift Runtime 和 Rust Runtime 的外部插件投递要求驱动声明 `delivery.poll`、最近 15 秒内登记/心跳且会话最近 45 秒在线并未归档；否则回退 Mesh mailbox。Rust Runtime 另有内置 Codex worker：已登记的 managed Codex 会话可进入队列，不依赖插件心跳；它会等空闲、必要时恢复会话并调用 `turn/start`。Swift Runtime 没有这个内置消费者。隔离 Broker + 真实 Unix socket + Swift Runtime 的测试验证队列中的 room、正文、消息 ID；Rust 测试覆盖无领取能力、离线、过期与正常接收。测试没有启动厂商 Agent，队列接收不代表消费。投递后驱动崩溃时消息可能留在 Runtime 队列，同一目标和正文的已入队重试可返回原记录，即使驱动已离线；不同内容或目标复用该键会拒绝。确认丢失导致的两条路径重复、断线恢复和旧队列迁移仍待验证。

## Codex 特有路径与边界

[MeshHooks](../../../../Sources/Pharos/MeshHooks.swift) 支持 Codex hook：SessionStart 映射 idle，UserPromptSubmit、工具及压缩相关事件映射 busy，PermissionRequest 映射 blocked，SessionEnd 根据原因映射 stopped 或 gone。PostToolUse 可在上下文中提示未读定向消息；Stop 输出 `decision: block` 和 reason，引导运行 `pharos mesh recv`，不是直接证明消息已被模型消费。是否安装并触发 hook、实际状态时效、桌面 roster 更新和最终回复入 room 均需按具体会话实测。

旧 [Codex adapter](../../../../Sources/PharosRuntime/Adapters/Codex/CodexBackendAdapter.swift) 有 `turn/start` 的 Thread 投递方法，但桌面 Thread 当前走上述 Mesh 路径，不能把该方法存在等同于当前产品端到端通过。Codex Session App Server 事件也未自动等同于 Mesh member presence。

Rust Runtime 的内置 worker 还会在重启时把中断的 `accepted` Codex 消息恢复为 queued；它调用 `turn/start` 返回后标记 consumed，不代表助手完成。该实现及隔离队列测试不等于真实 Thread 往返通过。Swift Runtime 则无此 worker。

## 真实隔离房间回复与沙盒边界（2026-11-07）

以独立 Broker、独立 Rust Runtime 和真实 Codex 持久 Session `01a1b79f-16eb-70a2-9ab8-72556581dea8` 复测回复：用户消息成功进入 Runtime，记录为 consumed；Agent 在 `workspace-write`、`approvalPolicy=never` 下按提示执行指定的 `pharos-mesh send`，该命令明确以清空环境和临时路径限定到测试 Broker，但退出码为 1，输出 `Cannot reach the Mesh broker.`；隔离 room 未观察到 Agent 回复。目标 Session 后续真实回合 completed，助手说明命令失败；探针因未收到预期回复标记超时，不能记为成功。证据 `internal/evidence/2026-11-07_codex-thread-roundtrip.log`。

进一步在独立会话用同一隔离 Broker 路径实测：宿主 Python 对 Unix socket `connect` 成功；由真实 Codex `workspace-write` 工具进程运行的只连接 socket 的独立 Python 命令返回 errno 1（EPERM）。两次诊断均收到助手标记及 completed；后一次核对了命令包含 Python、AF_UNIX、connect 和该测试 socket 路径。日志在 `internal/evidence/2026-11-07_codex-thread-socket-diagnostic-final.log`。该证据支持本机该沙盒配置阻止 socket 连接，不代表所有 Codex 配置或平台都一样。CLI 目前把 connect 错误折叠为不可连接，不能单凭 CLI 错误区分拒绝、缺失或断连。

结论：当前依赖 Agent 自己调用 Mesh CLI 的 room 回复方案在此真实沙盒里不可用；接收消息和 Session 内回复已验证，但真实 Thread 往返尚未完成。当时需要具备会话、原消息、房间与完成回合关联的宿主侧回复通路；后续实现与验证见下一节。诊断复现：构建后在原有探针环境中追加 `PHAROS_CODEX_THREAD_SOCKET_DIAGNOSTIC=1`；若使用 `PHAROS_CODEX_THREAD_REPLY_TEST=1` 则会运行仅针对临时房间的真实 CLI 回复探针。两种运行都会创建保留的 Codex 测试 Session。


## 宿主侧回复与真实往返（2026-11-07）

Rust Runtime 为每条定向投递持久保存目标 member ID 和 `turn/start` 返回的 turn ID。只有该回合 `completed` 后，才从该 turn 中选择 `agentMessage.phase=final_answer` 的非空正文；普通 Session 回合、其他 turn、思考和中间消息不会转发。宿主通过打包的 `pharos-mesh host-reply` 从 stdin 发送，避免在进程参数中暴露正文，也不依赖沙盒内 Agent 连接 socket。正文中出现的 `@` 不会触发新的定向投递。

**Product Mesh（2026-11-09）**：`host-reply` 在 `PHAROS_DISTRIBUTED_MESH=1` 下将同一 say-once stdin 信封映射到 `DistributedAgentChat.replyOnce`（`MeshDistributedHostReply`）；不再要求 legacy Broker。`MeshHostThreadBinder` 绑定 Codex 时固定使用 builtin `codex:app-server`，不另建 host-thread driver。受控映射测试 `testDistributedHostReplyMapsSayOnceOntoReplyOnce` 通过；legacy Broker `testHostReplyCLIReadsRequestToEOF` 仍通过。**not-tested**：真实 Codex app-server 经新 host-reply 的完整 product 往返。

Broker 的 `say-once` 检查已加入房间的成员 ID、原消息真实的目标 member ID、回复引用和幂等键；远程请求需通过现有控制凭据。已提交相同回复的重试返回成功，不会再写一条；相同键配不同内容、目标或原消息会拒绝。回复记录与原消息引用写入 room 历史，Runtime 保存 pending/posted 状态；Broker 暂时不可用会重试。消息必须是修改后带稳定 `targetMemberIDs` 的定向消息，旧记录缺少目标 ID 时不会自动转发；无 turn ID、没有 final_answer、失败回合和超大正文也不会伪造回复。Runtime 旧版持久投递缺少目标快照时不会自动转发。

隔离真实测试 Session `01a1b7ac-5229-7162-b682-c0f5cf3e3485`：Broker 将 @agent 发给真实 Codex，Agent 不调用消息工具，Runtime 收到 consumed 并确认目标 turn completed，宿主将最终标记写回同一隔离 room，历史中回复者和原消息 ID 均匹配。摘要在 `internal/evidence/2026-11-07_codex-host-relay-final-verified.log`。并发 24 次相同请求、重复请求、不同成员/正文、重建 Broker、无认证远程请求，以及重建 Runtime 后的 turn/member/room 关联均有隔离测试；Rust Runtime 14 项和 MeshCore 126 项回归通过。上述测试不是跨机器验收；后续桌面 WebKit 复测见下一节。

剩余边界：真实远程节点路由和凭据、桌面展示、分布式 Mesh、Agent 意外自行发送重复消息、Broker 与 Runtime 的网络故障及提交确认丢失后的真实恢复仍待实测；已有单元测试不能等同这些生产场景。进程在 `turn/start` 已被 Codex 接受但 Runtime 尚未记录 turn ID 时崩溃，仍可能重试启动，不能承诺端到端恰好一次。旧消息和不支持 final_answer phase 的后端不会自动补发；应在迁移和界面中明确状态。运行 `PHAROS_CODEX_THREAD_LIVE_TEST=1 python3 Tests/Live/codex_thread_probe.py` 会创建保留的测试 Session，需先构建两个 Rust helper 和 Swift `pharos-mesh`。

## Runtime 成员身份冲突（2026-11-07）

Swift 与 Rust Runtime 的 `delivery.submit-member` 若有多个符合在线条件的会话匹配同一 member ID，原先选择最近更新的会话，不能证明目标正确。现在新投递遇到多个候选会返回错误，不写入任何 Runtime 队列；只剩一个有效候选后正常路由。已有幂等键的重试仍返回原记录，避免把已接受的投递重新导向其他会话。隔离 Swift Broker + 真实 Runtime socket 测试确认冲突时回退 mailbox，Rust 测试覆盖拒绝和冲突解除；对应输出 `internal/evidence/2026-11-07_runtime-ambiguous-swift-final.log`、`internal/evidence/2026-11-07_runtime-ambiguous-rust-retest.log`。

回退 mailbox 仍以同一个 member ID 寻址：如果多个消费者共享该 ID，不能保证领取者身份；本次只消除 Runtime 按更新时间盲选，不证明端到端无误投。现有已入队记录不会自动迁移，真实多主机冲突、修复身份及重连仍需验证。Antigravity 的 Mesh→ACP 桥仍未完成。

## 派生会话身份与桌面绑定（2026-11-08）

当前 [OpenAI App Server 文档](https://developers.openai.com/codex/app-server)区分可寻址的 `thread.id` 与可能表示根会话的 `thread.sessionId`。Rust Runtime 原先优先读取后者：受控根/派生数据复现两个会话被登记为一个，见 `internal/evidence/2026-11-08_codex-fork-routing-before.log`。现要求使用非空 `thread.id`，缺失时不猜测；受控测试核对分别登记并路由到派生 ID，Rust Runtime 16 项通过（`...codex-thread-binding-rust-final.log`）。这不自动修复旧 Runtime 已持久化的错误记录，升级时应核对既有绑定；不删除或迁移用户数据。

隔离 Broker 与真实 Codex Session 测试中，根 `01a1bacd-69ff-7713-9a40-164db7f886f6` 和派生 `01a1bacd-7c0c-7631-8bce-ae275be42332` 分别登记，消息经 Runtime 进入派生会话，助手回复写回原房间，根会话没有测试回复（`...codex-fork-thread-live.log`）。本机返回的 fork 数据未观察到 `sessionId` 与根 ID 相同，因此这次真实测试证明目标隔离，不独立复现受控测试中的共享根字段。

Thread 右侧添加 Session 入口现也接受本机 Codex：Broker 必须声明 `thread-session-binding-codex-v1`，本机 Rust Runtime 必须声明 `codex-thread-id-v1`；旧 Broker 或 Runtime 不提供 Codex 候选。提交前核对本机清单、目标会话、Runtime 唯一归属及 member ID；Runtime 未绑定时使用精确的 provider thread ID，已绑定时使用已确认的 member ID。存在其他 owner、重复会话或 member 冲突则拒绝；Broker 再以锁保护昵称与绑定冲突。Runtime 快照与 Broker 写入并非跨进程原子事务，跨进程同时改绑尚未验证，不能宣称彻底消除该竞态。

真实本机 Session `01a1bad2-c259-7922-b3a1-a94aae29d89a` 从程序操作的桌面右栏添加并完成 Thread 唯一关联回复（`...codex-thread-bind-ui-seeded-retry.log`）。随后根 `01a1bad8-18b6-7242-b549-b0e01ae9bd07` 的派生 Session `01a1bad8-2be2-7823-af72-b7254bbfcbbd` 经相同界面添加，回复和引用在 Thread 可见、Broker 唯一，根会话没有回复标记（`...codex-thread-bind-fork-ui-seeded.log`）。测试 Session 保留，不是物理鼠标或真实远程验收。
